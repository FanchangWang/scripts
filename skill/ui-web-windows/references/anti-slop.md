## 允许 vs 禁止的审美来源

- **允许**：用户提供的品牌色 / Logo；项目已有 token；Fluent 2 / Windows 11 组件范式；1–3 个色相（含中性色）。
- **禁止**：凭空发明"高级感"；从记忆里抄某个知名网站的配色；用形容词（clean / modern / premium / elegant）作为设计决策依据。

如果项目没有任何审美输入，**先问用户**：单色 + 一个强调色 / 温暖中性 / 冷峻工具风 等，锁定后再写代码。

## 设计决策记录

把决策写进项目已有的 agent 指令文件（`AGENTS.md` / `CLAUDE.md`）。若项目没有这类文件，询问用户后创建 `DESIGN.md`。记录内容：

```markdown
## Design decisions (ui-web-windows)

- 审美方向：<如"克制工具风"，一句话>
- 主题模式：system / light / dark / user-switchable
- 品牌基色：<hex>，强调色 token：--accent
- 色相数量：≤3（含中性色）
- 字体：Segoe UI Variable + Microsoft YaHei UI；字重 400/600
- 间距：4px 栅格（4/8/12/16/24/32）
- 控件高度：24 / 32 / 40（三选一）
- 圆角：控件 4px，卡片 8px
- 主题实现：light-dark() + :root[data-scheme]，meta color-scheme 已声明
- 禁用模式：B1–B10 全部生效
- 验证命令：<项目实际命令，如有>
```

token 的具体值留在 `tokens.css`，指令文件只记录决策与索引，不复制颜色值。

## 文案规则

- 所有字符串必须是**真实的产品文案**：结合应用功能、用户动作和上下文写。
- 按钮 / 标签用 sentence case（"Save changes"，不是 "Save Changes"）。
- 错误信息说明**发生了什么、用户能做什么**，例如："Couldn't save changes. Check your connection and try again."
- 空状态给出下一步动作，不要只写 "No data"。
- 用户明确要求某种语气（活泼 / 正式）时再调整；否则默认克制、具体。
- 中文界面使用自然的简体中文，不要中英夹杂堆术语。

## 自查（生成后逐项打勾）

- [ ] 没有 B1–B10 中的任何模式。
- [ ] 所有颜色 / 间距 / 圆角来自 token，组件里无裸 hex / 任意 px。
- [ ] 浅色和深色都检查过，深色不是简单反转。
- [ ] 文案是真实内容，无占位符和营销空话。
- [ ] 字体是 Segoe UI Variable 栈，字重 600 而非 700。
- [ ] 决策已记录到项目指令文件。

## AI 默认审美指纹（具名清单，出现即 FAIL）

以下是其他 agent 最常见、且**不属于 Windows 设计语言**的默认组合。它们来自对主流模型输出的归纳（Anthropic `frontend-design` 等）；在本 skill 里出现即视为照搬模板：

- 暖米色背景（约 `#F4F1EA`）+ 高对比衬线大标题 + 赤陶色（约 `#D97757`）强调色。
- 近黑底（`#0B0B0B` / `#111`）+ 酸性绿或朱红点缀。
- SaaS 卡片套件：所有卡片同圆角、同 `rgba(0,0,0,.1)` 阴影、渐变底色 wash。
- 模板 chrome：字距拉开的 ALL-CAPS eyebrow 小标签、中点元信息 `A · B · C`、破折号片段 `WORD — fragment`、等宽字体数据标签、链接后追加 `→`。
- 装饰性编号 `01/02/03`：只有内容本身是真实序列时才允许；边框、分隔线、eyebrow 都必须承载信息，不是为了好看。

**排版层面的默认痕迹**：标题里只给一个词加强调色；按钮/标签全大写；内容上方多余的小标签。行宽上限 <80 字符，Windows 推荐 50–60 字符；衬线字体行宽可略长、行高略大。

## 两遍法与克制

不要拿到需求就写代码：

1. **第一遍**：先出紧凑方案——4–6 个具名 hex、字体角色、一句话布局概念 + ASCII 线框、对齐方式、2–3 条原则。把决策写进设计记录。
2. **第二遍**：自问"换一个通用 prompt，我会不会得到几乎相同的方案？"如果会，说明方案没有针对**主题 / 行业 / 受众 / 具体任务**做取舍，回到第一遍修订。需求里没有这些信息时，先提出一个并请用户确认。
3. **然后才写 UI**。完成后用截图自查（"一张截图胜过一千个 token"），并做"出门前摘掉一件配饰"的删减：删掉任何不服务于需求的装饰。
4. **大胆只用在一处**：一个页面只让一个元素成为焦点，其余保持克制；不要每块都抢注意力。
5. **动效编排**：一次协调的入场 / 揭示优于散落的 fade-and-slide；动效要回应用户动作，不要自顾自循环。

## 文案的正面规则

除了禁用占位文案，还要做到：

- 主动语态、以用户视角命名（"管理通知"，不是"webhook 配置"）。
- CTA 写出结果（"保存更改"，不是"提交"）；同一流程里动词保持一致。
- 错误说明**怎么修**，不道歉、不含糊；空状态是一次行动邀请，而不是"暂无数据"。
- 搜索零结果不要伪装成有数据返回。

## 迭代方式

设计系统一旦锁定就是**硬约束**，不是建议。后续迭代只探索布局 / 结构 / 内容方向，不改视觉风格；用 `branch`（给出备选方向）与 `replace`（优化选中方向）分开推进，由用户决定是否继续分支。CSS 类名特异性冲突（`.section` 与 `.cta` 互相抵消 padding/margin）是常见破版原因，改样式前先检查选择器优先级。
