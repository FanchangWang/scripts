# EnvSwitch

Windows 多版本环境变量切换器 + PATH 整理工具。一个 exe 同时提供**本地网页 GUI**和 **CLI**，使用 .NET 10（LTS）。

各功能的完整执行流程（含每步判断、失败点、边界）见 [FLOWS.md](FLOWS.md)。

## 功能

- 读取**用户**与**系统**环境变量：网页「环境变量」页把两者分组列出（点标题可折叠分组），支持筛选，并可**行内编辑值**（保存前二次确认，展示原值与新值）或**删除变量**（删除后就地置灰、标「已删除」并撤掉按钮，不重读整表，页面滚动位置不变）；变量值是目录/文件路径但目标已不存在时，变量名后标「已失效」。值按**注册表原样**显示：`REG_EXPAND_SZ` 的 `%USERPROFILE%\go` 就显示成 `%USERPROFILE%\go`，编辑保存也保持这个写法，不会被固化成展开后的绝对路径。
- 管理多套工具链（Java / Node / Maven …），每套可配置：
  - 要生成的环境变量名（如 `JAVA_HOME`）与 PATH 条目模板（如 `%JAVA_HOME%\bin`）；两者**都可留空**，留空表示这套工具链不写环境变量 / 不写 PATH
  - 是否生效（关闭 = 相当于没配置过这套工具链）
  - **环境变量作用范围**与 **PATH 作用范围**，各四档：`用户`、`系统`、`用户唯一`、`系统唯一`（唯一 = 写本侧并把另一侧的残留清掉）
  - 多个版本；每个版本可配 Home（环境变量值）和**多条 PATH 条目**（版本没填显式条目时回退用模板展开 Home）
- 切换版本时自动：设置环境变量 → 清理该工具链所有旧版本的 PATH 条目 → 写入当前版本条目 → 排序去重（与 `path` 命令默认一致；不想要排序可把 `settings.sortPathOnApply` 设为 `false`，只去重）。
- **同一版本里指向同一目录的多种写法只写一条**：一个版本可以填多条 PATH，若其中几条其实指向同一个真实目录（典型是 `…\latest\jdk-21\bin` 这类 junction / 软链别名与 `…\jdk-21.0.13.0.2\bin` 这种真实目录），按配置顺序只保留**最靠前且目录存在**的那一条（第一条不存在就用后面第一条存在的），其余同目录写法会从 PATH 里一并删除，不再重复堆积。判定靠解析真实路径（穿透 junction，含路径中间的软链），不是比字符串。
- **保存配置前校验路径**：每个版本的 Home、版本里的每条 PATH 条目、以及「该版本没填条目时才用到」的 PATH 模板（先把 `%环境变量名%` 换成 Home、再展开 `%USERPROFILE%` 这类系统变量），只要看起来是路径却不存在，就整份拒绝保存，并返回逐条错误（网页上对应输入框描红）；判断按真实目录分组，同一组的写法只要有一条存在就放行（反正写入时只会用那一条）。同一工具链里**版本重名**也会被拒绝保存（切换时按名字找不到唯一版本）；**工具链重名**同样拒绝（重名会让状态读取与批量应用指向不清的那一套）；`settings.port` 不在 0–65535 也拒绝保存。切换版本写 PATH 前也会再挡一次旧配置里残留的不存在条目。
- 环境变量值里的 `%变量%` 会先展开再写入：`Path` 与 `JAVA_HOME` 的取值口径一致——若该变量当下不是 `REG_EXPAND_SZ`（系统不会替我们展开），写入前先换成实际路径；展开后仍有 `%`（引用了不存在的变量）直接拒绝，不会出现「保存成功、切换成功、实际是无效字符串」。「环境变量」页保存单个变量时按同一口径处理：能展开成真实路径的就展开并提示，展不开的按原样存但会标成「已失效」并说明原因，不会让界面显示「正常」而实际无效。
- **部分写入会如实报告**：切换时环境变量写成功、PATH 被拒（或反之），消息会点明「已写入 JAVA_HOME（用户），这部分不会回滚」，不会让人以为整次都没写；「唯一」模式删掉另一侧同名变量同样算已发生的副作用，会写成「已写入 X（用户·唯一），并删除了系统侧同名变量」。批量应用（`all` / 「立即应用全部」）某一侧写到一半失败时也按同样口径列出已经落盘的项，并且**写入与删除分开说**（「该侧已写入 JAVA_HOME、删除 PHP_HOME，未回滚」），不会把一次删除写成「已写入」。
- **存在性判断统一 1.5 秒上限，且多条一起探测**：「环境变量」页的「已失效」标记与 PATH 页的失效探测都走同一个带超时的探测入口。值指向断网的网络盘或拔掉的移动硬盘时，`Directory.Exists` 本身能卡十几秒（实测单条 19 秒），加了上限后一次请求最多等 1.5 秒，超时按「存在」处理，绝不误删。两页的探测都是并发跑的（各一轮 `Parallel.ForEach`），所以有 N 条坏值不会变成 N × 1.5 秒——但并发度受 CPU 核数限制：条数 ≤ 核数时一轮 1.5 秒，更多会分轮（4 核 + 60 条全坏约 22 秒，仍远好于串行的 90 秒）。本机实测 3 条黑洞 UNC 值，`/api/env` 由串行约 4.5 秒降到 1.5 秒。
- **PATH 里的 `%变量%` 会换成具体路径**：Windows 只有在 `Path` 值是 `REG_EXPAND_SZ` 时才会展开条目里的 `%USERPROFILE%` 这类变量；若 `Path` 是普通字符串（`REG_SZ`，很多机器上就是），写进去只是一条无效路径。所以写入 PATH 时（版本切换、PATH 工具页「应用写入」、`path --apply`）会把这侧不会自动展开的 `%变量%` 条目换成实际路径再写，且只在「原写法本身无效、展开后确实存在」时替换，其余条目原样保留；PATH 工具页的「当前」列表会把这类条目标成 `→ 实际生效的是 …`。
- 通过直接写注册表（`HKCU\Environment` / `HKLM\…\Session Manager\Environment`）并在写入后广播一次 `WM_SETTINGCHANGE`（最多等 200ms）落盘，新开的终端立即生效；不调 `Environment.SetEnvironmentVariable`，因为它每次写都要向所有顶层窗口广播并逐个等响应，本机实测单次可拖到 20 秒以上。**批量应用（`all` / 网页「立即应用全部」）是一次性处理**：先把两侧变量与 PATH 读成内存快照，逐套工具链在内存里算完，再按侧一次性写注册表，最后只广播一次（10 套工具链也只有 1 次，不是每套 2 次）。
- CLI：`list` 看当前配置、`use` 切换某个版本（环境变量 + PATH 一起写）、`all` 一次性应用全部生效工具链（默认就写，加 `--dry-run` 只预览）、`path` 查看系统与用户两侧 PATH 的处理结果（默认只预览，加 `--apply` 才写）。环境变量的查看与编辑在网页「环境变量」页；`env` 命令已移除。
- 首次运行自动探测本机 Java 安装（读取 `release` 文件，不执行任何 exe）生成默认配置。

## 构建（单文件绿色 exe）

需要 .NET SDK 10 或更高（SDK 11 可编译 `net10.0` 目标）：

```powershell
cd dotnet/EnvSwitch
dotnet publish -c Release -o publish
```

产物为 `publish/EnvSwitch.exe`，自包含、单文件，拷到任意 Windows x64 机器即可运行，无需安装 .NET。

## 运行

```powershell
# 直接启动网页界面（默认行为），自动打开浏览器
.\EnvSwitch.exe

# 指定端口、不自动开浏览器
.\EnvSwitch.exe serve --port 5180 --no-browser

# 列出工具链 / 版本 / 当前值
.\EnvSwitch.exe list

# 切换版本（环境变量与 PATH 一起写；--dry-run 仅预览）
.\EnvSwitch.exe use Java 17 --dry-run
.\EnvSwitch.exe use Java 17

# 一次性应用所有「生效且有激活版本」的工具链（环境变量 + PATH 一起写，
# 等同网页的「立即应用全部」）
.\EnvSwitch.exe all --dry-run
.\EnvSwitch.exe all

# 查看系统 + 用户两侧 PATH 的处理结果（默认只预览，不写入）
.\EnvSwitch.exe path

# 确认无误后写入：系统与用户两侧一起写（只写一侧会让条目错位，所以没有 --scope）
.\EnvSwitch.exe path --apply

# 可选：关掉排序 / 去重
.\EnvSwitch.exe path --no-sort --no-dedup
.\EnvSwitch.exe path --no-sort --no-dedup --apply

# 某一侧「当前有条目、处理后 0 条」时 --apply 会拒绝（避免把整侧 PATH 清空）；
# 确实要清空那一侧，再加 --allow-empty
.\EnvSwitch.exe path --apply --allow-empty

# 指定配置文件
.\EnvSwitch.exe --config D:\envswitch.json list
```

配置文件默认位于 `%LOCALAPPDATA%\EnvSwitch\config.json`（本机 `C:\Users\guyue\AppData\Local\EnvSwitch\config.json`），可用 `--config` 覆盖。

## 配置格式

```json
{
  "toolchains": [
    {
      "name": "Java",
      "envVar": "JAVA_HOME",
      "pathTemplate": "%JAVA_HOME%\\bin",
      "enabled": true,
      "envScope": "User",
      "pathScope": "User",
      "active": "17",
      "versions": [
        {
          "name": "8",
          "home": "C:\\Program Files\\Java\\jre1.8.0_513",
          "paths": [
            "C:\\Program Files\\Java\\jre1.8.0_513\\bin",
            "C:\\Program Files (x86)\\Common Files\\Oracle\\Java\\java8path"
          ]
        },
        { "name": "11", "home": "C:\\Program Files\\Zulu\\zulu-11-jre" },
        { "name": "17", "home": "C:\\Program Files\\Java\\jdk-17" }
      ]
    }
  ],
  "settings": {
    "normalizePathOnApply": true,
    "sortPathOnApply": true,
    "pathScope": "User",
    "openBrowserOnStart": true,
    "port": 0
  }
}
```

## 权限说明

- 修改**用户**环境变量无需管理员权限；工具链的作用范围选到「系统」或以管理员运行才能改系统变量。
- `envScope` / `pathScope`（每套工具链各自设置）：`User` 写用户、`Machine` 写系统；`UserOnly` 写用户并删除系统侧同名变量 / 本工具链条目；`MachineOnly` 反之。四值都可用，只是写系统侧需要管理员。
- `settings.normalizePathOnApply`（切换版本时是否整理 PATH）：开启后每次切换都会把整条 PATH 排序并去掉重复项（去重不区分大小写、忽略尾部 `\`），与 `path` 命令默认一致；关闭则按「原有条目 + 新版本条目」原样拼接。`settings.sortPathOnApply`（默认 `true`）单独控制「要不要排序」：设为 `false` 时只去重、保留原有顺序，适合担心同名 exe（`python`、`java`、`git`）改从别的目录命中的情况。这两项都在「项目配置」页。
- PATH 去重按 Windows 规则大小写不敏感。
- 配置文件保存为「先写 `config.json.tmp` 再整体替换」，中途异常不会留下半份 JSON。**读取失败分三种处理**：内容真的坏了（JSON 语法/结构错）才把原文件备份成 `config.json.bad-<时间戳>` 并用默认配置继续——**备份本身失败就不写回**（原文件保持原样，只用内存里的默认配置干活），免得把一份还能手工修复的文件覆盖掉；只是「暂时读不到」（被其它程序占用、杀软扫描、没有读权限）会先重试一次，仍失败则**报错停下、不写回默认配置**——网页接口返回 503 并说明「未做任何修改」，CLI 打印原因并以退出码 1 结束；**路径本身不可用**（断开的网络盘、拔掉的 U 盘、无权限的目录）按「读不到」处理，**不会**被当成首次运行而往那儿写一份新的默认配置。这里的「看不见」由 `ConfigStore.ClassifyMissing` 统一判定，`Load` 与 `config` 命令共用：默认路径与裸文件名（`--config cfg.json`，等于当前目录）永远按「还没建」创建；其它路径先做一次 **1.5 秒上限**的目录探测，不可达立刻报错（实测黑洞 UNC 43ms，旧写法人均等 21 秒的 SMB 超时）。
- 网页服务只监听 `127.0.0.1`，不对外暴露；同时有**三道请求闸**：`Host` 只认 `127.0.0.1` / `localhost` / `[::1]`（挡 DNS rebinding），`POST` 只收 `application/json`（挡浏览器可免预检的 `text/plain` 盲打），带 `Origin` 且非同源一律 403。
- 出异常不再「空 500」：统一返回 `{"ok":false,"message":"服务内部错误：…"}` 并在控制台留一行日志；请求体不是合法 JSON 返回 400 而不是 500。
- 「环境变量」页里不是字符串类型的值（`REG_DWORD` / `REG_MULTI_SZ` / `REG_BINARY` 等）只读展示类型名，**不允许编辑**（写回会把类型改成字符串），但仍可删除；这类值请用 `regedit` 修改。

## 网页界面

界面为左右结构：左侧菜单、右侧内容区（宽度自适应、不限制最大宽度）。地址栏用路径记录当前页（`/switch`、`/project`、`/toolchain`、`/path`、`/env`，也兼容 `?page=env` 和 `#/env`），刷新或直接输入地址都会停在同一页；点击任意菜单都会重新读取最新配置与该页数据后重绘，保证在别处改过的内容立刻可见。

提示统一在页面顶部：轻提示（成功 5 秒、失败 12 秒后自动消失，点一下立即关闭）浮在窗口顶部居中；切换失败、保存被拒、批量应用结果这类需要反复看的，还会在内容区顶部留一条常驻横幅。

| 菜单 | 用途 |
|---|---|
| 版本切换 | 点版本按钮切换，先弹二次确认（列出会写入的变量、PATH 条数与作用范围，并说明是否仅为预览）；切换结果（成功 / 失败原因）常驻显示在页面顶部；「不生效」的工具链不显示 |
| 项目配置 | 全局设置：端口、启动时自动开浏览器、切换版本时排序去重（排序可单独关掉，只保留去重） |
| 工具链配置 | 顶部提示「改完不会立即生效」+「立即应用全部」（保存配置后把**所有**「生效且有激活版本」的工具链逐个应用，结果逐条列出）；左侧工具链列表，右侧「基础配置」（一行一项：名称 / 环境变量名 / PATH 模板 / 是否生效 / 环境变量作用范围 / PATH 作用范围，每项下方有 ℹ️ 解释）与「版本列表」（表格列序：删除 / 激活单选 / 版本名 / Home / PATH 条目，删除按钮在行首，「添加版本」在表格下方） |
| PATH 工具 | 系统/用户 PATH 并排列表（当前 / 处理后）；目录已不存在的条目在「当前」列表标「已失效」，并在「处理后」自动剔除；同一个目录的不同写法（软链别名与真实目录）按真实目录算一条，只留靠前的那条；可排序、去重后勾选写入（默认「仅预览，不写入」，取消勾选后点「应用写入」会先二次确认要写的系统/用户条数，确认后整体覆盖） |
| 环境变量 | 用户与系统变量分组展示，点分组标题折叠/展开；支持筛选、行内编辑值（保存前二次确认）、删除变量（二次确认后就地置灰、标「已删除」并撤掉操作按钮，不重读整表，滚动位置不变）；值指向的目录/文件已不存在的变量标「已失效」（保存后按新值立即重算）；`REG_DWORD` 等非字符串类型只读展示、不可编辑；`Path` 这一行**不能在这里清空或删除**（会把该侧所有命令弄废），要改请到「PATH 工具」页 |

### PATH 工具规则

页面分「当前」「处理后」两栏，每栏同时列出「系统」与「用户」列表：

1. 系统与用户中**完全相同**的条目，从用户的「处理后」列表自动移除（「当前」列表中以"与系统重复 · 已移除"徽标标出）。
2. 同一工具链（依据配置里的版本 Home 识别）但**版本不同**时，两侧条目都加橙色"版本冲突"徽标，例如 `Java 17 ↔ 21`。
3. 「处理后」列表每行可勾选是否保留，勾选结果即为写入内容；默认勾选「仅预览，不写入」：勾着的时候点「应用写入」只按当前勾选重算一遍并提示会写多少条，**不改系统**；想真正落盘先取消这个勾选。它的用途是批量清理 / 排序前先看一眼结果，确认无误再写。**空列表护栏**：两侧都没勾选时直接拒绝（否则就把 PATH 清空了）；某一侧原本有条目、处理后一条不剩时会单独再确认一次「这一侧 PATH 会被整条清空」。
4. 「排序」「去重」开关影响「处理后」列表，改动后自动刷新。去重会忽略尾部目录分隔符并保留不带 `\` 的规范形式（盘符根 `C:\` 与 UNC 根除外），因此 `C:\Program Files\GitHub CLI` 和 `C:\Program Files\GitHub CLI\` 视为同一项，只保留前者。
5. 每条条目都会检查目录是否还在：已不存在的在「当前」列表标「已失效」，并被自动从「处理后」列表剔除，写入时不会带上（因此历史软件卸载后残留的 PATH 会被清理掉）。
6. 「去重」按**真实目录**判断：`…\latest\jdk-21\bin` 这种 junction / 软链别名与它指向的 `…\jdk-21.0.13.0.2\bin` 会被算成同一项，只保留列表中靠前的那条（保留原写法，不会替换成解析后的真实路径）。
7. 条目里含 `%USERPROFILE%` 这类变量时：若该侧 `Path` 是 `REG_EXPAND_SZ`，系统会自己展开，写法原样保留；若是 `REG_SZ`（不会自动展开），「当前」列表会标出 `→ 实际生效的是 …`，「处理后」与写入内容直接换成具体路径。
8. 「应用写入」只提交了系统或用户一侧时，**另一侧保持原样**；两侧都没提交会被接口拒绝（避免误清空整条 PATH）。提交的一侧是**整体覆盖**：勾选结果就是写入后的完整内容。接口还会先过滤空值：`[null]`、`[""]` 这种「给了元素但全是空值」的列表直接 400 拒绝（否则写进去就是一个空字符串，等于把整侧清空）；真要清空某一侧，提交那个**空数组**并在页面上过二次确认。CLI 的 `path --apply` 有对应护栏：某一侧「当前有条目、处理后 0 条」（条目全失效被剔除）时直接拒绝并说明是哪一个侧，确需清空那一侧要显式加 `--allow-empty`。
